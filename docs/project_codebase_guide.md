## 1. AEGIS in one page

**Problem.** During urban floods, the signals that matter arrive from many
systems at once — rain gauges, river gauges, traffic feeds, citizen reports.
They use different formats, units and clocks, arrive continuously, and some
are wrong, late or missing. Someone has to turn them into one consistent,
explainable picture of "which area is at risk right now, and why".

**What AEGIS does.** It is a Big Data pipeline that:

1. **ingests** four heterogeneous event streams through **Apache Kafka**;
2. **validates and standardises** them with **Apache Spark** (one set of rules
   for streaming and batch), quarantining bad records with a reason;
3. **integrates** them per geographic zone (a 40-cell grid over Chennai) using
   spatial joins and Haversine distances;
4. computes an **explainable, rule-based risk score** per zone and time window;
5. stores operational data in **HBase** (wide-column, row-key access) and
   history in a **Parquet data lake** (bronze → silver → gold);
6. trains a small **Spark MLlib** decision tree as a supporting component;
7. serves everything through a **FastAPI** backend (REST + Server-Sent Events)
   to a **React + Leaflet** dashboard.

**Three data modes, each in its own folder and always labelled.**

| Mode | Folder | What is in it | Live streaming? |
|---|---|---|---|
| Synthetic (default) | `data/` | everything generated by the project's simulator | yes (Kafka + Structured Streaming) |
| Real historical | `data_real/` | real ERA5 hourly rain, IMD + NOAA daily rain, DFO + GDACS flood events (Nov–Dec 2023, Cyclone Michaung); water level, traffic, reports **absent** | no (batch only) |
| Hybrid | `data_hybrid/` | the real data above + **synthetic** water level, traffic, reports and incidents simulated *from the real ERA5 rain* | no (batch only) |

**Honesty rules built into the code:** every synthetic record carries
`"synthetic": true`; every canonical row carries `data_source` and
`observation_type`; a missing indicator never counts as "safe"; ML labels are
synthetic in every mode and labelled as such; the dashboard shows which mode
it is serving.

### 3.2 How the synthetic world works (`producers/world.py`)

* **Rain**: a sum of moving Gaussian "storm cells". Intensity at a point =
  `peak · sin(π·life_fraction) · exp(−d² / (2·radius²))`.
* **Wetness** per location integrates rain with a time constant τ = 6 h:
  `W ← W·e^(−Δt/τ) + rain·τ·(1 − e^(−Δt/τ))`.
* **River level** = `base_level + gain · W`; **flood hazard** = `clamp((W − 40) / 120, 0, 1)`.
* **Traffic** speed drops with rain, flooding and rush hour; disruption text is
  chosen from the speed ratio and hazard.
* **Incidents** per zone and step follow Poisson rates that grow with rain² and
  hazard²; each produces 0–3 delayed, jittered citizen reports (35 % verified,
  55 % unverified, 10 % rejected).
* **Severity label** (flood-related incidents only):
  `latent = 0.40·clamp(rain_3h/60) + 0.35·hazard + 0.15·clamp(recent/4) + 0.10·traffic_disruption + N(0, 0.07)`,
  cut at 0.28 / 0.60 / 0.84 into Low / Moderate / High / Critical.

The model in § 8 never sees `latent`, `hazard` or the true rain; it only sees
the noisy sensor observations the ETL computes.

### 3.3 Raw formats (deliberately heterogeneous)

| Version | Timestamp | Units / shape | Example fields |
|---|---|---|---|
| `wx-metric-1` | ISO with `+05:30` | °C, mm/hr, flat lat/lon | `event_id, source_id, event_time, temperature_c, humidity_pct, rainfall_mm_hr, condition` |
| `wx-imperial-2` | epoch milliseconds `ts_ms` | °F, inches/hr, nested `location`, METAR sky codes | `obs_id, station, location.latitude, temp_f, rh_pct, precip_in_hr, sky` |
| `wl-1` | ISO UTC `Z` | level in m, cm or ft per sensor | `water_level, unit, danger_level, sensor_status, river_id` |
| `tr-1` | `yyyy-MM-dd HH:mm:ss` local, **no offset** | km/h, veh/km | `avg_speed_kmph, free_flow_speed_kmph, vehicle_density, disruption` |
| `pr-1` | ISO `+05:30` | free-text category, optional coordinates | `report_id, category, channel, verification_status, confidence` |
| `hi-1` | ISO UTC | canonical category + severity | `incident_id, category, severity, affected_area_km2` |
| `wx-era5-1` | ISO UTC (end of hour) | mm in the hour, °C, % | real ERA5 + provenance fields |

### 3.4 Volumes and rates (measured)

* Backfill: 60 days, 15-minute steps, 2 % defects → weather 69,600 · water
  46,375 · traffic 173,926 · incidents 6,916 = **296,817 lines**.
* Live: 4 events/s, 6 % defects, 3 % late events; the simulated clock runs
  **18× faster** (a 6-hour storm in 20 minutes), but every event is stamped
  with the *real* time so Spark's event-time logic behaves as with live sensors.

### 3.5 Validation, missing values, duplicates, anomalies

`spark_jobs/transforms.canonicalize()` applies the same rules in batch and
streaming:

* every raw JSON leaf is parsed as a **string** and cast explicitly, so
  `"rainfall_mm_hr": "heavy"` becomes `invalid_type:rainfall` instead of
  breaking the record; only syntactically broken JSON is `malformed_json`;
* **12 rejection codes**: `malformed_json, unknown_source_type,
  unknown_schema_version, topic_source_mismatch, missing_required,
  invalid_type, invalid_timestamp, future_timestamp (> 5 min ahead),
  invalid_coordinates, outside_study_region, out_of_range, invalid_unit`;
* **8 non-fatal flags** on valid rows: `late_arrival, sensor_degraded,
  sensor_fault, unknown_category, unknown_condition, missing_coordinates,
  missing_optional, unknown_status`;
* missing optional measurements stay **NULL** — never invented;
* duplicates: batch keeps the first arrival per `event_id`
  (`dedup_batch`); streaming uses `dropDuplicatesWithinWatermark(event_id)`;
* rejected records go to `quarantine/{batch,stream}` with the raw payload
  (≤ 2,000 chars) and their reasons.

Measured: injected defects = detected defects for all 8 kinds (e.g.
malformed_json 640/640, duplicates 1,944/1,944) on the 296,817-record backfill.

### 3.6 Retries and failure handling at ingestion

* Producer: librdkafka retries (10, back-off 500 ms, delivery timeout 60 s);
  `BufferError` → back-pressure loop; final failure → appended to
  `data/dead_letter/producer_failures.jsonl`; `replay_dead_letter` re-sends.
* Producer start-up refuses to run if the broker is unreachable or topics are
  missing (exit 2) — topics are never auto-created (`KAFKA_AUTO_CREATE_TOPICS_ENABLE=false`).
* Real-data import: any HTTP or format error stops the import with
  `ok: false`; nothing synthetic is substituted (§ 3.1).

## 4. Kafka and event-driven processing

### 4.1 Topics (`config/aegis.yaml` → `kafka.topics`)

| Topic | Written by | Read by | Purpose | Retention |
|---|---|---|---|---|
| `weather-events` | producers | streaming | raw weather | 7 days |
| `water-level-events` | producers | streaming | raw river levels | 7 days |
| `traffic-events` | producers | streaming | raw traffic | 7 days |
| `incident-reports` | producers | streaming | raw citizen reports | 7 days |
| `zone-risk-updates` | streaming (`zone_risk`) | API live feed | scored zone windows (JSON) | 2 days |
| `data-quality-events` | streaming (`bronze_dq`) | API live feed | per-batch DQ metrics | 2 days |

3 partitions each, replication factor 1 (single broker, KRaft mode, no ZooKeeper).

### 4.2 Producer and message format

* Value: the raw JSON payload (UTF-8 text); key: the source id
  (`formats.event_key`), so all events of one station land in one partition
  and keep their order.
* Settings: `acks=all`, `enable.idempotence=true`, `linger.ms=20`, lz4.
* **Guarantee: at-least-once** from producer to broker. Idempotence stops
  retry duplicates inside the broker; the pipeline still de-duplicates on
  `event_id` because the generator deliberately sends duplicates.

### 4.3 Consumers and offsets

| Consumer | Group / offsets | Behaviour |
|---|---|---|
| Spark Structured Streaming (3 queries) | no consumer group; offsets stored in each query's **checkpoint** (`data/checkpoints/<query>`) | first start `earliest`, later from checkpoint; `maxOffsetsPerTrigger = 20,000`; `failOnDataLoss=false` |
| API live feed | group `aegis-api-live-<random>`, `auto.offset.reset=latest`, no commits | only new updates matter for the live dashboard |
| `kafka_consumer_check` | group `aegis-verify`, earliest, commits | verification |

### 4.4 When Kafka is down

Producers exit with a clear error (or dead-letter records that fail later);
the streaming queries fail and are restarted from their checkpoints with
back-off 10, 20, 40, 60 s (max 5 restarts, counter reset after 10 healthy
minutes); the API keeps serving from HBase/Parquet and the dashboard falls
back to polling; `/api/pipeline/status` reports "Kafka unreachable".

### 4.5 One event through Kafka (real names)

Z-R04-C02) → `formats.weather_event` → JSON

### 5.3 Structured Streaming in detail

Three independent queries, each with its own checkpoint, all reading the same
four topics (`spark_jobs/streaming_pipeline.py`):

1. **`bronze_dq`** (stateless, `foreachBatch`): archives every raw record to
   `bronze/kafka_raw` (partitioned by topic and ingest date) — nothing is ever
   dropped here; runs `canonicalize`; writes invalid rows to
   `quarantine/stream`; writes per-batch counts to `live/dq_metrics`, the
   `data-quality-events` topic and HBase `processing_metrics`.
2. **`silver`**: valid rows → `withWatermark("event_time", "10 minutes")` →
   `dropDuplicatesWithinWatermark(["event_id"])` → `silver_stream/<domain>`
   (partitioned by `event_date`) and HBase `sensor_observations` /
   `incident_records`; the number of HBase rows written is compared with the
   batch count and two rows are read back.
3. **`zone_risk`**: valid, de-duplicated rows → `zone_signals()` (stream-static
   join with the nearest-station map) → `groupBy(window(event_time, "5 minutes"), zone_id)`
   in **update** output mode → `score()` → HBase `zone_risk_history`
   (`zone_id#live#window_start_ms`), `live/zone_risk`, topic
   `zone-risk-updates`, and `state/zone_risk_latest.json`.

* **Trigger**: every 10 s (or `availableNow` for `--available-now`).
* **Event time vs processing time**: windows use `event_time` from the
  payload (converted to UTC), not arrival time.
* **Watermark**: 10 minutes behind the newest event time seen. Older events
  are dropped by the stateful operators (dedup, windows) — measured, e.g. 8
  rows "dropped by watermark" in one batch — but query 1 still archives them
  and flags them `late_arrival`, so the batch layer includes them.
* **Exactly-once?** No claim. Offsets are checkpointed and a failed batch is
  re-run (at-least-once). HBase puts are idempotent (same row key), and Parquet
  appends are guarded by per-batch marker files (`_aegis_batches/<id>.done`) so
  a replayed batch is not appended twice.
* **Monitoring**: a `StreamingQueryListener` writes progress to
  `state/streaming/status.json`: exact Kafka records per batch (from offset
  ranges), trigger time, state rows, rows dropped by the watermark.
* **Shutdown**: SIGTERM / `STOP` file → each query waits for its in-flight
  batch, then stops (measured 37 s on 2026-10-21, inside the 90 s grace period).

### 5.4 Why Spark rather than plain Python/pandas or a database

| Option | Why not for AEGIS |
|---|---|
| plain Python loops | no parallelism, no event-time windows, no checkpoints |
| pandas | single machine, in memory; no streaming, watermarks or fault-tolerant state |
| database-only (e.g. SQL triggers) | streaming windows, schema mapping of 6 formats and ML in one engine would be awkward |

Honest scale: ~300,000 backfill records and 4 events/s live run comfortably on
one machine (`local[8]` batch, `local[4]` streaming). Spark is used because the
course is about distributed processing and because the same code would scale
out on a cluster unchanged — no distributed run was measured.

## 6. Data lake (bronze / silver / gold)

| Layer | Path under `data/lake/` | Content | Written by |
|---|---|---|---|
| Bronze | `bronze/files/topic=…` | raw generated lines exactly as read | batch ETL |
| Bronze | `bronze/kafka_raw/topic=…/ingest_date=…` | raw Kafka value, key, partition, offset, timestamp | streaming `bronze_dq` |
| Quarantine | `quarantine/batch/domain=…`, `quarantine/stream/quarantine_date=…` | rejected rows, reasons, raw payload | ETL, streaming |
| Silver | `silver/<domain>/event_date=…` | canonical, validated, de-duplicated rows (batch) | ETL |
| Silver | `silver_stream/<domain>/event_date=…` | the same from streaming | streaming `silver` |
| Gold | `gold/zone_hourly`, `zone_hazard_history`, `zone_risk_hourly`, `zone_daily`, `incident_daily`, `incident_hour_of_day`, `traffic_hazard_correlation`, `rainfall_disruption_bands`, `ml_training_flood_severity`, `dq_report` (+ real: `real_daily_rainfall`, `station_daily_rainfall`, `official_events`) | analytics-ready aggregates | ETL / real_data_layers |
| Live | `live/zone_risk`, `live/dq_metrics`, `live/ml_predictions` | streaming outputs | streaming / inference |

**Why Parquet**: columnar (read only the columns a chart needs), compressed
(snappy), typed schema stored in the file, partition pruning by date, readable
by Spark and by pyarrow in the API without Spark.

**Historical vs incremental**: batch tables are rebuilt with
`mode("overwrite")` (static partition overwrite) — simple and reproducible;
streaming tables are append-only. The batch ETL can include the archived
Kafka bronze, so live data also reaches the gold layer.

**One record through the layers**: a `wx-imperial-2` line
`{"obs_id":"WX-…","station":"AWS-09","ts_ms":…,"location":{…},"temp_f":84.2,"precip_in_hr":0.5,…}`
→ bronze row (`value` = that text, `topic = weather-events`, `origin = file:weather.jsonl`)
→ `canonicalize`: `event_id` ← `obs_id`, `source_id` ← `station`,
`event_time` ← `timestamp_millis(ts_ms)`, `temperature_c = (84.2 − 32)·5/9 = 29.0`,
`rainfall_mm_hr = 0.5 × 25.4 = 12.7`, `zone_id` from lat/lon, `is_valid = true`
→ silver `silver/weather/event_date=…` → `zone_signals` assigns it to every zone
whose nearest weather station (≤ 12 km) is AWS-09 → `gold/zone_hourly`
(`rainfall_avg_mm_hr` for that zone-hour) → `gold/zone_risk_hourly`
(rainfall indicator) → `/api/analytics/historical` and the map.

## 7. HBase

### 7.1 Tables (`aegis/storage/hbase_repository.py → TABLES`)

| Table | Row key | Families (versions, TTL) | Written by | Read by |
|---|---|---|---|---|
| `sensor_observations` | `source_id#event_ts_ms(13 digits)#event_id` | measurement, location, metadata (1, 30 d) | streaming `silver`, ETL `--write-hbase` (last 2 days) | integration test, verify script |
| `incident_records` | `incident_id` | incident (1), location (1), verification (**3**) | streaming, ETL | `GET /api/incidents/{id}` |
| `zone_risk_history` | `zone_id#series#window_start_ms` (series = `live` or `hourly`) | risk (**5**), summary (1), quality (1) | streaming `zone_risk` (live), ETL (hourly) | `/api/zones`, `/api/zones/{id}` (history + cell versions) |
| `processing_metrics` | `component#metric_ts_ms` | metrics, status (1, 7 d) | streaming (each query, each batch) | `/api/pipeline/status` |
| `model_predictions` | `subject#(9999999999999 − ts_ms)#prediction_id` | input, output, meta | API predictions, zone inference | `/api/model/predictions` |

### 7.2 Why these row keys

* **Fixed-width 13-digit timestamps**: HBase sorts keys as bytes, so zero-padded
  numbers sort in time order; a scan of prefix `WXM-02#` returns that station's
  readings chronologically.
* **Source/zone first**: all rows of one sensor or zone are contiguous → cheap
  prefix scans; writes from many sensors spread across the key space.
* **`live` vs `hourly` series**: a batch hour and a live 5-minute window that
  start at the same instant would otherwise overwrite each other (a bug found
  and fixed during verification).
* **Reverse timestamp** for predictions: a forward scan returns the newest first.
* **Latest zone assessment**: `latest_with_prefix("zone_risk_history", "Z-R04-C02#live#")`
  = reverse scan, limit 1.
* **Versions**: `risk` keeps 5 versions, so the dashboard can show how one
  window's score changed as late updates arrived (update output mode).

### 7.3 Writes, reads, duplicates, failures

* Values are UTF-8 strings; `None` is not written → sparse rows cost nothing.
* Spark writes per partition (one Thrift connection, batched puts of 500) and
  checks the written count against the DataFrame count, then reads a sample back.
* Re-processing the same event writes the same row key → **idempotent**.
* Connection: retries with back-off (3 attempts); failure raises
  `HBaseUnavailable`.
* HBase down: with `hbase.fail_on_error: true` the streaming batch fails and is
  retried from the checkpoint after restart; the API falls back to the
  streaming snapshot file and the batch gold table and marks
  `read_from` / `source_errors`. Verified with a 75-second outage (2026-10-21).

### 7.4 Why HBase (and the trade-offs)

Strengths used here: row-key range scans for time series, many versions per
cell, TTLs, sparse wide rows, horizontal scaling by region splitting (not
exercised here). Costs: operational complexity (JVM, ZooKeeper, Thrift
gateway), no secondary indexes or SQL joins, standalone mode here (single
node, local filesystem). Alternatives and why not: [technology_stack_guide.md](technology_stack_guide.md).

## 8. Risk scoring

### 8.1 Formula (`aegis/risk.py`, weights in `config/aegis.yaml → risk`)

```
f_i  = clamp((value_i − low_i) / (high_i − low_i), 0, 1)        # per indicator
risk = 100 · Σ (w_i · f_i) / Σ w_i        over AVAILABLE indicators only
coverage = Σ w_i (available) / Σ w_i (all)
```

| Indicator | Input column | Weight | low → 0 | high → 1 | Meaning |
|---|---|---|---|---|---|
| rainfall | `rainfall_avg_mm_hr` | 0.30 | 2.5 | 50.0 | mean intensity in the window |
| water_level | `level_ratio_max` | 0.25 | 0.60 | 1.00 | river level / danger level |
| incidents | `weighted_reports` | 0.20 | 0 | 5 | verified 1.0, unverified 0.5, rejected 0 |
| traffic | `disrupted_ratio` | 0.15 | 0 | 0.75 | share of disrupted observations (blocked/flooded or speed < 40 % of free flow) |
| historical | `historical_hazard_index` | 0.10 | 0 | 1 | zone's archived flood incidents / max zone |

* **Categories** (lower bounds): Critical ≥ 75, High ≥ 50, Moderate ≥ 25, Low ≥ 0.
* **Confidence** from coverage: high ≥ 0.85, medium ≥ 0.60, low ≥ 0.40;
  below 0.40 → **"Insufficient data"**, no score.
* **Contributions** = points per indicator; they sum to the score.
* **Explanation**: the top three contributors in words, plus what was not observed.
* Weights and thresholds are demonstration values, not validated hazard science.

### 8.2 Worked examples (computed with `aegis.risk.assess`)

**A — everything observed.** rain 20 mm/hr, level 0.90 × danger, 2.5 weighted
reports, 50 % disrupted, hazard index 0.6.

| | rainfall | water | incidents | traffic | historical |
|---|---|---|---|---|---|
| f | (20−2.5)/47.5 = 0.368 | (0.90−0.60)/0.40 = 0.75 | 2.5/5 = 0.50 | 0.5/0.75 = 0.667 | 0.6 |
| w·f | 0.1105 | 0.1875 | 0.10 | 0.10 | 0.06 |
| points | 11.05 | 18.75 | 10.00 | 10.00 | 6.00 |

Score = 100 × 0.5580 / 1.00 = **55.8 → High**, coverage 1.0, confidence high.
Explanation: *"Score 55.8 (High, high confidence). Main factors: water level
0.90x danger level (+18.8); rainfall 20.0 mm/hr (+11.1); incident reports 2.5
weighted reports (+10.0)."*

**B — no river gauge and no traffic nearby.** rain 30, 4.0 weighted reports,
hazard 0.8. Available weight = 0.30 + 0.20 + 0.10 = 0.60 → coverage 0.60
(medium). f = 0.579, 0.80, 0.80 → Σ w·f = 0.1737 + 0.16 + 0.08 = 0.4137 →
score = 100 × 0.4137 / 0.60 = **68.95 → High**, *"Not observed: water_level, traffic."*

**C — rain only.** 45 mm/hr gives f = 0.895 but coverage 0.30 < 0.40 →
**"Insufficient data"**, no score. This is exactly what the real-data mode shows.

**D — dry day.** rain 1.0, level 0.5, no reports, no disruption, hazard 0.2 →
only the historical indicator contributes → **2.0 → Low**.

### 8.3 From observations to a zone score

1. `zone_signals()` turns each valid record into a signal row for a zone:
   weather → every zone whose nearest weather station within 12 km is the
   source; water level → zones with that gauge as nearest within 6 km
   (readings flagged `sensor_fault` are excluded); traffic and reports → their
   own zone.
2. `signal_aggregations()` per zone and window: mean/max rain, max level
   ratio, disrupted share, weighted reports, counts.
3. `score()` calls `assess()` per row through a Spark UDF (one definition for
   Spark, API and tests).
4. Batch: 1-hour windows (`gold/zone_risk_hourly`); streaming: 5-minute windows.

### 8.4 Measured vs calculated

Rainfall in mm/hr is a **measurement** (synthetic here, or ERA5 in real mode);
the risk score is a **calculated index**. Heavy rain alone does not mean a
flood: flooding depends on accumulated rain, drainage, river state and
location — which is why rain is only 30 % of the score and why rain alone
yields "Insufficient data", not "High".

## 9. Spatial analytics

* **Coordinates**: WGS84 latitude/longitude in decimal degrees; code uses
  `(lat, lon)` order everywhere (Leaflet also takes `[lat, lon]`). No
  projected CRS is used.
* **Zone grid**: bounding box 12.85–13.25 N, 80.10–80.35 E, cell 0.05° →
  8 rows × 5 columns = **40 zones**, ids `Z-R<row>-C<col>` (row 0 = south,
  col 0 = west). `zone = floor((lat − 12.85)/0.05), floor((lon − 80.10)/0.05)`,
  clamped at the north/east edge; a record whose coordinates lie outside the
  box is rejected as `outside_study_region` (a citizen report *without*
  coordinates stays valid, flagged `missing_coordinates`, but has no zone).
  Example: (13.05, 80.22) → row floor(4.0) = 4, col floor(2.4) = 2 → **Z-R04-C02**.
  The Python (`ZoneGrid.zone_for`) and Spark (`zone_id_col`) versions are tested
  to agree on 409 points including cell boundaries.
* **Haversine**: `a = sin²(Δφ/2) + cos φ1 · cos φ2 · sin²(Δλ/2)`,
  `d = 2R · asin(√a)`, R = 6371.0088 km. Implemented three times (Python,
  numpy, Spark) and tested for parity. Limitation: assumes a spherical Earth
  (error ≤ ~0.5 %), fine at city scale.
  Example: (13.05, 80.22) to (13.0827, 80.2707) = **6.586 km**.
* **Nearest-station assignment** (`spatial_analytics.nearest_station_map`):
  cross join zone centres × stations, Haversine distance, `row_number()` over
  distance per zone, keep rank 1 within the radius. Measured: 39 of 40 zones
  have a weather station within 12 km; 19 of 40 have a river gauge within
  6 km (the others report water level as *not observed*).
  Example: zone Z-R04-C02 → weather WXM-02 (0.75 km), gauge WLS-07 (0.15 km);
  WXM-02 also feeds Z-R04-C03 and Z-R04-C04.
* **Radius search**: `GET /api/incidents/nearby?lat=&lon=&radius_km=` (numpy
  Haversine, rejected reports excluded, nearest first) and
  `spatial_analytics --radius 3` (Spark). Measured: 236 hazards within 3 km of
  (13.05, 80.22).
* **Incident density**: incidents per km² of each cell (cell area from
  Haversine extents).
* **Map** (`RiskMap.jsx`): OpenStreetMap tiles; zones are Leaflet
  `Rectangle`s coloured by risk category (faint/dashed when stale or
  historical); incidents are `CircleMarker`s coloured by category with
  popups; clicking the map runs the nearby search; clicking a zone opens its
  detail. Zone geometry is served as `bounds` arrays, **not GeoJSON**.

Why spatial matters: a list of incidents does not tell a responder *where risk
concentrates*; joining every signal to the same zone, and only to nearby
stations, lets AEGIS compare areas and say "missing" honestly when no sensor
covers a zone.

## 10. Machine learning

| Question | Answer from the code |
|---|---|
| Target | severity of a flood-related incident: Low / Moderate / High / Critical |
| Labels | **SYNTHETIC** — `severity_rule` in the generator (§ 3.2). Not real outcomes |
| Algorithm | `pyspark.ml.classification.DecisionTreeClassifier`, gini, max depth 6, min 5 instances per node, seed 42 |
| Features (9) | `rain_3h_mm, rain_max_1h_mm_hr, level_ratio_max_3h, humidity_avg_3h, disrupted_ratio_1h, speed_ratio_avg_1h, reports_6h, water_obs_available, traffic_obs_available` |
| Point-in-time | features use only hourly buckets that end before the incident's own bucket and reports strictly before the incident time |
| Leakage guard | `FORBIDDEN_FEATURES` (label, severity, ids, time, category, archived counts…) are rejected before training |
| Pipeline | `Imputer(median, fitted on train only) → VectorAssembler → DecisionTree → IndexToString`; labels indexed with a **fixed** mapping Low=0…Critical=3 |
| Split | **time-based**: newest 20 % of incidents = test (cutoff 2026-10-11 02:41 UTC) |
| Persistence | `models/flood_severity_dt/<version>/pipeline` + `metadata.json` + `latest.json`; reloaded and checked on 25 rows |
| Serving | API loads the latest model in a local Spark session (`local[1]`, 768 MB); `POST /api/model/predict`; zone inference `--zones` |
| Missing weather at inference | zone gets **no prediction** ("insufficient_data") instead of an imputed "rainy" median |

**Measured (synthetic mode, backfill only, 2026-10-22, identical to 2026-10-21):**
1,822 rows (train 1,457 / test 365) · accuracy **0.677** · weighted F1 **0.664**
· majority baseline 0.323 · per-class F1 Low 0.875, Moderate 0.541, High 0.333,
Critical 0.787 · tree depth 6, 69 nodes · top importances rain_3h_mm 0.713,
reports_6h 0.118, rain_max_1h 0.053.

Confusion matrix (rows = actual, columns = predicted: Low, Moderate, High, Critical):
Low [105, 11, 2, 0] · Moderate [16, 49, 19, 3] · High [1, 30, 21, 23] · Critical [0, 4, 9, 72].

What the metrics mean here: how well a tree recovers the generator's hidden
rule from noisy sensor features — **not** real-world flood-forecasting skill.
"High" is hardest because it sits between two neighbouring classes on a
continuous latent score.

**Other modes:** real mode has no real labels, so no model is trained or
served; hybrid mode trains on synthetic labels driven by real rain (accuracy
0.842, but the test set has 1 High and 0 Critical case — see
[ml_model.md](ml_model.md)).

ML data flow: `gold/ml_training_flood_severity` → validate → time split →
fit → evaluate → save + reload check → `latest.json` → API `ModelService`
→ `POST /api/model/predict` / `GET /api/model/predictions` → ML model tab.
Diagram: [batch_ml_workflow.png](batch_ml_workflow.png).

**ML ≠ rule-based risk.** The risk score is a transparent formula over zone
indicators; the ML model predicts incident severity from features. They are
computed independently and shown side by side; neither feeds the other.

## 13. Docker and infrastructure

| Service | Image | Ports | Depends on | Notes |
|---|---|---|---|---|
| `kafka` | `apache/kafka:4.3.1` (KRaft) | 9092 (host), 29092 (internal) | — | healthcheck `kafka-broker-api-versions`; volume `kafka-data`; 1 GB |
| `hbase` | `aegis-hbase:2.5.16` | 9090 Thrift, 16010 UI, 9095 | — | healthcheck Thrift port + master UI; volume `hbase-data`; 2 GB; ZooKeeper session 120 s |
| `streaming` | `aegis-spark:3.5.9` | 4040 Spark UI | kafka, hbase healthy | restart unless stopped; stop grace 90 s; 3 GB |
| `producers` | `aegis-spark` | — | kafka healthy | `run_all --rate 4`; 512 MB |
| `api` | `aegis-spark` | 8000 | kafka, hbase | 2 GB |
| `api-real` / `api-hybrid` | `aegis-spark` | 8001 / 8002 | none (profiles `real` / `hybrid`) | HBase and live feed off |
| `tools` | `aegis-spark` | — | (profile `tools`) | one-off jobs: `docker compose run --rm tools …` |

* The project folder is bind-mounted at `/app`, so code and `data*/` are shared with the host.
* Service discovery: containers reach `kafka:29092` and `hbase:9090` by name;
  host tools use `localhost:9092` / `localhost:9090`.
* No secrets: the local stack has no credentials; `.env.example` holds placeholders only.
* Shutdown: `scripts\stop_all.ps1` (graceful), `-Down` removes containers,
  `-Down -DeleteVolumes` also deletes Kafka/HBase data.
